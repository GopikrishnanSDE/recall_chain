MEDCHAIN SUPPLY CHAIN — PROJECT OVERVIEW
=========================================
Generated by Claude Code, 2026-10-02


WHAT THIS IS
------------
MedChain is a blockchain-based medicine supply-chain traceability and
anti-counterfeiting system. It tracks a medicine batch from manufacturer
through supplier, distributor and seller, lets patients verify a pack is
genuine using a scratch code (no crypto wallet needed), and gives
manufacturers an accountable recall mechanism with a closure report.


ARCHITECTURE — THREE APPS IN ONE REPO
--------------------------------------
medchain-supply-chain/
  backend/   Hardhat project: the Solidity smart contract, tests, deploy script
  client/    Next.js 16 + React 19 dashboard: the UI everyone interacts with
  server/    Express + ethers.js: stores scratch-code fingerprints, builds
             Merkle proofs, relays patient claims

How they talk to each other:

  Browser (staff: producer/supplier/distributor/seller/owner)
     |  MetaMask signs transactions
     v
  SupplyChain.sol  <----------------+  (read-only queries)
     ^                              |
     |  relayed tx (server pays gas)|
  Express server --------------------+
     ^
     |  plain HTTP, no wallet
  Browser (patient, Verify page)


THE SMART CONTRACT
-------------------
File: backend/contracts/SupplyChain.sol  (Solidity 0.8.19, ~500 lines)

Roles
  Supplier, Producer, Distributor, Seller. Only the contract owner
  (deployer) can register them via addSupplier/addProducer/
  addDistributor/addSeller. O(1) role lookup via actorIdOf[address][role].

Products = batches
  addProduct(name, description, quantity, merkleRoot) — only a registered
  producer can create one. Moves through a strict linear pipeline:
      Created -> Processing -> InTransit -> ForSale -> Sold
  Each transition is gated to the correct role:
      supplyProduct, processProduct, distributeProduct, listForSale,
      markProductSold
  Each batch has exactly ONE supplier/producer/distributor/seller — no
  fan-out to multiple pharmacies in this model.

Scratch-code verification (Feature 3)
  Every pack (serial 1..quantity) gets a random 32-byte secret. Each
  secret is hashed into a "leaf":
      keccak256(keccak256(abi.encode(serial, secret)))
  All leaves are folded into one Merkle root, stored on-chain per batch.
  unitStatus(...) is a free view function that recomputes the leaf from
  a submitted secret + proof and checks it against the root — this is
  cryptographically provable and cannot be faked by the server.

Unit claim (Feature 9)
  The first genuine check of a pack can "claim" it to an anonymous
  customer key (no personal data on-chain) via claimUnit (direct wallet)
  or claimUnitFor (relayed by the server, verified by an EIP-191
  signature). A second check of the same code shows "already used" —
  this is how cloned/copied codes get caught.

Recall with confirmation (Feature 5)
  Only the producer that created a batch can call
  recall(productId, reasonHash) — this is PERMANENT, there is no
  un-recall. Every address that touched the batch becomes a "holder"
  who must quarantineUnits(...) (report what they physically pulled off
  shelves) and ackRecall(...) before a deadline (recallWindow, default
  24h, owner can shorten to 60s for demos). After the deadline, anyone
  can escalate a holder who didn't confirm — a permanent mark against
  that address (missedRecalls).

Closure report (Feature 10)
  closureReport(productId) returns: quantity, quarantined, claimed,
  claimedBeforeSale, unaccounted, and holder ack/escalation counts.
  These numbers always add up correctly (quarantined + claimed +
  unaccounted = quantity).

Tests: backend/test/SupplyChain.ts — 33 passing tests cover all of the
above.


THE CLIENT (Next.js dashboard)
-------------------------------
Pages, all under client/src/app/:

  /register-roles   Owner only. Register supplier/producer/distributor/
                     seller wallet addresses.
  /order-materials   Producer only. Create a batch; scratch codes are
                     generated entirely client-side; leaf hashes get
                     uploaded to the server; a printable CSV of codes
                     downloads to your machine.
  /supply-materials  Supplier -> Producer -> Distributor -> Seller, in
                     order. Advance a batch through each pipeline stage.
  /track-materials   Any staff member. Look up a batch, see its full
                     pipeline progress, and this is where the QR code
                     for that batch is generated.
  /recall            Producer initiates a recall; any holder
                     (supplier/producer/distributor/seller who touched
                     the batch) quarantines stock and confirms; shows
                     the live closure report.
  /verify            PATIENTS. No wallet needed. Type only the scratch
                     code; the server works out which batch/pack it
                     belongs to automatically. Shows Genuine /
                     Already-used / Recalled / Invalid, lets you claim
                     the pack, and shows full batch provenance (who
                     handled it, when, current stage).


THE SERVER (Express + ethers.js)
----------------------------------
File: server/src/index.js — all REST routes:
  GET  /api/health
  GET  /api/batches/:id
  GET  /api/batches/:id/provenance   (product info, actors, timeline, recall)
  POST /api/batches/:id/leaves       (producer uploads leaf hashes)
  GET  /api/batches/:id/proof/:serial
  POST /api/verify                   (patient scratch-code check)
  GET  /api/units/:id/:serial        (public recall-status lookup, no code)
  GET  /api/claim-digest
  POST /api/claim                    (relayed patient claim, server pays gas)

File: server/src/chain.js — connects to the blockchain RPC, holds a
"relayer" wallet that pays gas for patient claims (so patients never
need ETH or MetaMask).

File: server/src/store.js — stores each batch's leaf hashes as a local
JSON file under server/data/. The actual scratch-code secrets are NEVER
stored here — only hashes, which reveal nothing on their own.


DESIGN PRINCIPLE: WHERE SECRETS LIVE
--------------------------------------
  On-chain (contract):       Batch Merkle root, unit claim state,
                              recall state — nothing secret.
  Server (server/data/*.json): Leaf HASHES only, never the secrets
                              themselves.
  Browser only / printed CSV:  The actual scratch-code secrets (generated
                              by crypto.getRandomValues in the producer's
                              browser) and the patient's anonymous claim
                              key.
This means no single compromised system (server breach, chain reorg,
etc.) can leak every valid scratch code for a batch — only the printed
CSV can do that, and it's handled like a password list.


CHANGES MADE DURING THIS SESSION
-----------------------------------
1. Fixed a real bug in client/src/lib/web3.ts: the "switch network"
   button always hardcoded MetaMask's RPC to port 7545 (Ganache) even
   though this setup runs a Hardhat node on port 8545 — this caused the
   "wrong network" / "unable to connect" errors. Now it maps chain ID
   to the correct RPC URL, overridable via NEXT_PUBLIC_RPC_URL.

2. QR code now redirects instead of dumping raw JSON
   (client/src/app/track-materials/page.tsx): it encodes a link to
   /verify?batch=<id> instead of a JSON blob — QR for navigation only,
   scratch code for authenticity, kept strictly separate (scanning a
   QR never reveals a secret).

3. Added NEXT_PUBLIC_APP_URL (client/.env.local) so the QR always
   points at a reachable address (the LAN IP) instead of whatever
   happened to be in the staff member's own browser tab at the time.

4. New provenance endpoint (GET /api/batches/:id/provenance) and a
   matching card on the Verify page — shows product info, every actor
   who has handled the batch so far, a timestamped journey timeline
   (who did what, when, with the tx hash), and recall status — all
   automatically, as soon as the page knows the batch (e.g. right
   after a QR scan), no wallet or scratch code required yet.

5. Scratch-code-only verification: POST /api/verify no longer requires
   a batch ID or serial number. The server works out which pack a code
   belongs to by hashing it against every serial in the (optionally
   known) batch — no new secrets are stored anywhere to do this. The
   Verify page's form is now a single field.


HOW TO RUN IT LOCALLY
------------------------
1. Install dependencies in each folder:
     cd backend && npm install
     cd ../client && npm install
     cd ../server && npm install

2. Start a local blockchain:
     cd backend && npx hardhat node
   (listens on http://127.0.0.1:8545, chain ID 1337)

3. Deploy the contract (in a new terminal):
     cd backend && npx hardhat run scripts/deploy.ts --network localhost
   This writes the contract address into client/src/deployments.json.

4. Start the server (in a new terminal):
     cd server && RPC_URL=http://127.0.0.1:8545 npm start
   (listens on http://localhost:4000)

5. Start the client (in a new terminal):
     cd client && npm run dev
   (listens on http://localhost:3000)

6. In MetaMask, add a network:
     Name:      Hardhat Local
     RPC URL:   http://127.0.0.1:8545
     Chain ID:  1337
     Currency:  ETH
   Then import one of the test accounts below to act as owner/producer/
   supplier/distributor/seller.

HONEST LIMITATIONS (worth knowing before a real deployment)
----------------------------------------------------------------
  - The chain records what people REPORT. A holder can claim it
    quarantined packs without actually doing so — spot checks and
    real-world penalties are the only check on this.
  - A cloned/copied code verifies successfully exactly once; the second
    person to check it is warned, but the system cannot tell which
    physical pack is the real one.
  - A thief who scratches a genuine pack before it reaches a seller
    "owns" the claim; this is flagged as claimedBeforeSale but not
    prevented.
  - Customers who never check their code cannot be alerted to a
    recall — the closure report makes this number visible but cannot
    shrink it.
  - The relayer (server) sees the scratch code when relaying a claim,
    so patients are trusting it not to claim the pack for itself.
    Patients can instead call claimUnit directly from their own wallet
    to avoid this trust requirement.
  - Each batch has exactly one seller — this model does not support a
    single batch being distributed across many retail pharmacies.
  - The scratch-code-only lookup (added this session) searches every
    uploaded batch when no batch ID is known; this is instant at demo
    scale but would need an index/cache before a real, long-running
    deployment with many batches.
